# Pear 项目管理系统 — 毕业设计代码验收文档

---

## 一、项目概述

### 1.1 项目简介

Pear 项目管理系统是一个基于 **Go + Vue.js** 的现代化企业级项目管理和团队协作平台，类似于轻量版 Jira/Teambition。项目从原有 PHP 版本重写而来，采用微服务架构，提供完整的项目管理、任务看板、甘特图、日程安排、文件管理、成员权限、实时通知等功能。

### 1.2 技术栈总览

| 层级 | 技术 | 版本/说明 |
|------|------|-----------|
| 前端框架 | Vue.js 2 | 渐进式 JavaScript 框架 |
| 状态管理 | Vuex | 集中式状态管理 |
| 路由 | Vue Router | 单页面路由管理 |
| UI 组件库 | Ant Design Vue | 企业级 UI 组件 |
| API 网关 | Go + Gin | 端口 :18000 |
| 用户服务 | Go + gRPC Server | 端口 :18881 |
| 项目服务 | Go + gRPC Server | 端口 :18882 |
| 通信协议 | gRPC + Protobuf | 服务间高性能通信 |
| 服务注册/发现 | Etcd 3.5 | 分布式 KV 存储 |
| 关系数据库 | MySQL 8 | 主数据存储 |
| 缓存 | Redis 6 | 会话/缓存/去重 |
| 实时通信 | WebSocket (gorilla) | 全双工长连接 |
| 代码生成 | Protoc + code_gen | 从数据库自动生成结构体 |
| 日志 | Zap + Lumberjack | 结构化日志 + 日志轮转 |
| 容器化 | Docker + Docker Compose | 一键部署 |

### 2.2 Go Workspace 多模块管理

项目通过 `go.work` 管理 5 个 Go Module：

```
ms_project/backend/
├── go.work
├── api/          → test.com/project-api    (API 网关)
├── common/       → test.com/project-common  (公共库)
├── grpc/         → test.com/project-grpc   (gRPC 生成代码)
├── user/         → test.com/project-user   (用户服务)
└── project/      → test.com/project-project (项目服务)
```

### 2.3 请求处理流程

```
用户请求 → Nginx → API网关(:18000)
                     │
                     ├─ JWT Token验证 (gRPC调用用户服务)
                     │   └─ TokenVerify → 解析 memberId/organizationCode
                     │
                     ├─ 业务处理 (直接操作数据库 / gRPC调用)
                     │   ├─ 简单CRUD: 直接 GORM 操作 MySQL
                     │   └─ 认证/跨域: gRPC 调用用户/项目服务
                     │
                     └─ 统一响应格式 {code, msg, data}
```

### 3.6 燃尽图模块（亮点功能）

| 功能 | API 端点 | 说明 |
|------|----------|------|
| 项目报告 | POST /project/project/_getProjectReport | 燃尽图数据 |

**代码位置**：
- 后端 API：`backend/api/api/project/project.go` → `projectReport()` 函数
- 前端页面：`frontend/src/views/project/space/overview.vue`（33.91KB）
- 前端图表：`v-charts`（VeLine 折线图组件）

**功能描述**：在项目概览页面展示燃尽图，直观反映项目剩余任务量随时间的变化趋势，帮助团队评估项目进度和风险。

**技术细节**：

1. **燃尽图算法**：
   - 时间范围：从项目创建日期到当前日期，最多显示 60 天
   - 每日未完成任务数 = 累计新建任务数 - 累计已完成任务数
   - 理想基线：从首日总任务数线性递减到 0

2. **数据源**：
   - 新建任务：按 `ms_task.create_time` 按日分组统计
   - 完成任务：优先按 `ms_task.done_time` 按日分组统计
   - 旧数据回退：若 `done_time` 为空（历史数据），回退使用 `ms_project_event` 表中 `event_type='task:done'` 的记录
   - 起始偏移：计算时间范围之前的已有任务数和已完成数，作为累计初始值

3. **SQL 关键实现**：
   ```sql
   -- 每日新建任务
   SELECT DATE_FORMAT(FROM_UNIXTIME(create_time/1000),'%Y-%m-%d') AS date, COUNT(*) AS cnt
   FROM ms_task WHERE project_code=? AND deleted=0
   GROUP BY DATE_FORMAT(FROM_UNIXTIME(create_time/1000),'%Y-%m-%d')

   -- 每日完成任务
   SELECT DATE_FORMAT(FROM_UNIXTIME(done_time/1000),'%Y-%m-%d') AS date, COUNT(*) AS cnt
   FROM ms_task WHERE project_code=? AND deleted=0 AND done=1 AND done_time > 0
   GROUP BY DATE_FORMAT(FROM_UNIXTIME(done_time/1000),'%Y-%m-%d')
   ```
   > 使用 `DATE_FORMAT` 而非 `DATE()` 是为了兼容 MySQL `only_full_group_by` 严格模式，并避免 GORM 将 `DATE()` 结果解析为带时区的 `time.Time` 字符串导致 map 键不匹配。

4. **API 返回数据结构**：
   ```json
   {
     "date": ["2026-03-18", "2026-03-19", ...],       // 日期数组
     "undoneTask": [10, 8, 7, ...],                    // 每日未完成任务数
     "baseLineList": [10, 9, 8, ...]                   // 理想基线
   }
   ```

5. **前端渲染**：
   - 使用 `v-charts` 的 `ve-line` 折线图组件
   - 双折线：实际未完成任务数（实线）+ 理想基线（虚线）
   - 异步加载，loading 状态展示

#### RBAC 权限体系详解

系统采用基于角色的访问控制（Role-Based Access Control），通过 `ms_project_auth`（角色表）+ `ms_project_auth_node`（角色-节点关联表）+ `ms_project_member.authorize`（用户角色字段）三级结构实现细粒度权限控制。

**权限生效的三层机制**：

1. **菜单 API 按角色过滤**：用户登录获取菜单时，后端根据角色权限节点过滤菜单树，无权限的菜单不返回，前端不会渲染该菜单项
2. **API 接口权限校验**：后端 `NodeVerify` 中间件校验请求所需的权限节点，无权限返回 code=4031
3. **前端路由权限守卫**：`router.beforeEach` 检查路由的 `meta.permission`，无权限跳转 403 页面

| `frontend/src/router/index.js` | beforeEach 权限守卫 |

## 十、答辩问题准备

### 10.1 架构相关

**Q: 为什么选择微服务架构？**

A: 将系统拆分为 API 网关、用户服务、项目服务三个独立服务，原因如下：
1. **业务解耦**：用户管理和项目管理是两个独立的业务域，独立部署可以避免相互影响
2. **性能优化**：gRPC 基于 HTTP/2 和 Protobuf，比 JSON REST 性能更高
3. **弹性伸缩**：可以根据负载独立扩缩用户服务或项目服务
4. **技术异构**：每个服务可以独立选择技术方案

**Q: 为什么用 Go 重写？**

A: 
1. Go 的**并发性能**好，goroutine 轻量级，适合处理大量并发请求
2. **部署简单**，编译为单二进制文件，无需运行时环境
3. **标准库强大**，net/http、encoding/json 等开箱即用
4. 天然适合微服务，gRPC 对 Go 支持最好

**Q: API 网关的作用是什么？**

A: API 网关作为系统唯一入口，负责：
1. **统一认证**：JWT Token 验证中间件
2. **路由转发**：将请求路由到对应的 Handler
3. **协议转换**：前端 HTTP ↔ 后端 gRPC
4. **横切关注点**：CORS、日志、Recovery 等

### 10.2 通信相关

**Q: 前后端如何通信？**

A: 
1. **HTTP RESTful API**：主要通信方式，Axios 发起请求，统一前缀 `/project`
2. **WebSocket**：实时通知推送，前端 `socket.vue` 建立长连接
3. **Axios 拦截器**：统一处理 Token 注入和错误响应（401 自动登出）

**Q: gRPC 和 HTTP REST 有什么区别？**

A:
| 对比 | gRPC | HTTP REST |
|------|------|-----------|
| 协议 | HTTP/2 | HTTP/1.1 |
| 格式 | Protobuf (二进制) | JSON (文本) |
| 性能 | 高（3-10倍） | 一般 |
| 适用场景 | 服务间通信 | 对外API |
| 代码生成 | 自动生成客户端/服务端 | 手动实现 |

### 10.3 安全相关

**Q: 如何保证系统安全？**

A: 多层安全机制：
1. **JWT 双 Token**：Access Token + Refresh Token，支持无感续期
2. **ID 加密**：AES-CFB 加密数据库自增 ID，防止遍历攻击
3. **RBAC 权限**：基于角色的权限控制，`ms_project_auth` + `ms_project_auth_node`
4. **API 权限校验**：`NodeVerify` 中间件，对系统管理类接口进行节点级鉴权，无权限返回 code=4031
5. **菜单按角色过滤**：获取菜单 API 根据用户角色动态过滤，无权限的菜单不返回
6. **前端路由守卫**：`beforeEach` 检查 `meta.permission`，无权限跳转 403 页面
7. **操作鉴权**：`CanOperateProject` / `CanManageProject` / `CanOperateTask`
8. **CORS 白名单**：限制跨域请求来源
9. **软删除**：重要数据使用软删除，支持恢复

**Q: RBAC 权限控制是如何实现的？**

A: 三表结构 + 三层校验：

**数据模型**：
- `ms_project_auth`：角色表（管理员/编辑者/访客）
- `ms_project_auth_node`：角色-节点关联表（一个角色拥有多个权限节点）
- `ms_project_member.authorize`：用户角色字段（存储角色 ID）

**权限判定流程**：
1. `GetUserAuthId()`：从 `ms_project_member` 读取用户的 `authorize` 字段，取最大值，为空则用默认角色（编辑者）
2. `GetUserNodes()`：根据 auth_id 查询 `ms_project_auth_node` 获取权限节点列表
3. `HasNode()`：检查用户是否拥有指定权限节点

**三层校验**：
- **菜单层**：`FilterMenusByNodes()` 过滤菜单树，node 为空或 `#` 的菜单对所有人可见，父菜单只要有一个子菜单可见就保留
- **API 层**：`NodeVerify` 中间件校验，例如 `system.account` 保护账号管理接口，`system.menu` 保护菜单管理接口
- **路由层**：前端 `beforeEach` 守卫检查 `meta.permission`，匹配 `permissionNodes` 状态

**权限节点命名规范**：
- 菜单访问节点：`模块.子功能` 格式（如 `system.account`、`project.list`）
- 操作权限节点：`模块:操作` 格式（如 `task:create`、`file:upload`）

**Q: ID 加密是如何实现的？**

A: 使用 AES-CFB 对称加密：
- 加密：`EncryptInt64(id, key)` → 将 int64 转为字符串 → AES-CFB 加密 → hex 编码
- 解密：`Decrypt(cipherStr, key)` → hex 解码 → AES-CFB 解密 → 转为 int64
- 密钥：16字节 AES 密钥，统一 IV
- 效果：数据库 ID=1 对外显示为 "a1b2c3..." 格式，无法推测其他记录

### 10.4 功能相关

**Q: 任务看板拖拽如何实现？**

A: 
1. 前端使用 `vuedraggable` 库，监听拖拽事件
2. 拖拽完成后调用 `/task/sort` 接口，传递 `preCode`（被移动的任务）和 `nextCode`（目标位置后面的任务）
3. 后端重新计算所有任务的 sort 值，使用**事务**批量更新
4. 同样支持阶段拖拽排序（`/task_stages/sort`）

**Q: 实时通知怎么实现？**

A: 三层通知机制：
1. **WebSocket 推送**：前端 `socket.vue` 建立连接 → 后端 `handler.go` 管理连接 → 定时任务扫描到期任务 → 通过 WebSocket 推送
2. **邮件通知**：`email.go` 使用 gomail 通过 SMTP 发送 HTML 邮件
3. **站内通知**：写入 `ms_notify` 表，前端 HeaderNotice 组件展示未读数量

**Q: JWT 双 Token 机制是怎样的？**

A:
- **Access Token**：7天有效期，用于所有 API 请求认证
- **Refresh Token**：14天有效期，仅用于刷新 Access Token
- **自动续期**：前端路由守卫检测 Access Token 即将过期时，调用 `refreshAccessToken` 接口
- **验证流程**：中间件 `TokenVerify` → gRPC 调用用户服务 `TokenVerify` → 解析 Token 获取 memberId

**Q: 甘特图是怎么实现的？**

A: 前端使用自定义甘特图组件 (`gantt.vue`, 23KB)：
- 横轴为时间线，纵轴为任务列表
- 根据任务的开始/结束时间渲染条形图
- 支持按执行人分组、按阶段筛选

**Q: 演示数据是如何组织和关联的？**

A: 演示数据以虚构的"星辰科技"公司为背景，设计了一套完整的关联数据：
1. **组织架构**：1个公司组织 → 4个部门 → 部门成员关联
2. **项目体系**：5个不同类型项目，每个项目关联成员、阶段、任务、标签
3. **任务流转**：50个任务分布在不同阶段，模拟从"待处理"到"已完成"的全生命周期
4. **版本管理**：版本库 → 版本 → 关联任务 → 版本日志，完整的版本发布流程
5. **协作场景**：评论、工时、日程、通知等关联数据体现团队协作

**Q: 系统如何处理多组织/多租户场景？**

A: 
1. 每个用户可属于多个组织，通过 `ms_member_account` 表关联
2. 项目绑定到组织 (`organization_code`)，实现数据隔离
3. 切换组织后看到的项目和成员不同
4. 退出组织使用事务，同时清理成员账户、部门关系、项目成员关联

## 十三、总结

本项目从架构设计上采用了**微服务 + API 网关**的现代架构模式，技术栈覆盖了 Go gRPC、Etcd 服务发现、WebSocket 实时通信、JWT 认证、AES 加密等关键技术。在功能上实现了完整的项目管理闭环——从项目创建、任务看板、甘特图、权限控制到实时通知，是一个功能完备的企业级应用。

### 核心创新点

1. **微服务架构**：API 网关 + 用户服务 + 项目服务，gRPC 通信 + Etcd 服务发现
2. **JWT 双 Token 无感续期**：前端路由守卫自动检测并刷新
3. **AES ID 加密**：防止遍历攻击，保障数据安全
4. **WebSocket 实时通知**：任务到期提醒 + 逾期告警 + 邮件兜底
5. **大文件分片上传**：断点续传，提升用户体验
6. **命令面板**：类似 VS Code 的快捷操作
7. **@提及通知**：评论中 @成员触发实时通知
8. **RBAC 权限控制**：角色 + 节点的细粒度权限
9. **优雅启停**：信号捕获 → 服务注销 → 等待请求完成
10. **代码生成**：从数据库表自动生成 Go Struct 和 Proto Message
11. **完整演示数据**：预置10个账号、5个项目、50个任务的真实业务场景，含项目信息、工作流、资源链接等完整关联数据，支持开箱即用的功能演示和验收
